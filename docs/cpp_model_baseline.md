## 与 WBC 的对应

完整动力学等式为 `M * a + h = Sᵀ * tau + Jᵀ * f`，其中 a 是广义速度 v 的导数。支撑足加速度约束为 `J * a + Jdot * v = 0`。

`computeDynamics()` 使用四元数 free-flyer 的 q/v，接触 Jacobian 为 `LOCAL_WORLD_ALIGNED` 的线速度三行。基座 v 仍为局部表达，不能将前三维直接当作世界系速度；接触力与足端速度使用世界对齐坐标表达。CRBA 只使用上三角并显式对称化，动力学数据和接触运动学数据分别保存。

本实现保留现有 Python 模型中的 MJCF armature，并从 URDF 按关节名称取力矩/速度限制。没有将该模型当作 OCS2 的欧拉角基座模型；后续质心状态转换仍需显式适配。当前方法返回动态尺寸数组，尚未完成控制循环预分配及性能优化。

## C++ WBC 离线实现（2026-10-15）

源码已接入 `ros2/go2_control_cpp` 并通过 PR #13 合并，工作空间构建和下述离线对照均已通过，无需使用临时补丁。

### 实现与范围

- `include/go2_control_cpp/wbc.hpp`：基座/摆腿参考、QP、求解结果及控制器接口。
- `src/wbc.cpp`：完整浮动基动力学、支撑足加速度、摩擦/单边力/法向力上限、电机力矩限制；基座位置/姿态任务、摆腿前馈和反馈、接触力跟踪及正则。
- `src/osqp_solver.cpp`：原生 OSQP C API，采用 builtin 后端，polishing=true、max_iter=20000、warm_starting=false；稀疏结构相同则更新，变化时重新 setup。只接受 solved 状态并检查输出/约束。
- `src/wbc_replay.cpp`：从相同输入离线组装 QP、求解、导出矩阵和力矩；检查更新后的工作区与新建求解器结果一致，以及恢复原问题后的解一致。
- `examples/wbc/check_cpp_wbc.py`：调用现有 Python WBC 生成参考 QP 和结果，按关节名称对照 C++ 输出。
- `scripts/check_cpp_wbc.sh`：一条命令完成参考生成、定向构建、C++ 回放和 Python 比较。

保留现有 Python 数学问题和参数。四足为 42 个变量，两足为 36 个变量；接触力遵循传入的足名顺序。摆腿使用同一实测状态下的完整 Jacobian 数据，不重复计算质量矩阵。

C++ WBC 核心输出 QP 力矩；关节 PD、MRT 参考转换和 MuJoCo 控制循环由下述独立入口负责。默认的 Python/MuJoCo 控制入口没有改动，SDK2 尚未接入。上游任务定义和 SQP 对照仍按开发路线进行。

### OSQP 依赖

本机 Python `osqp` 包为 1.1.3，供 C++ 使用的 `libosqp` 为 1.0.0；它们是不同的版本指标。`environment.yml` 中显式声明 `libosqp>=1,<2`，本机已安装，无需重新安装环境。

CMake 通过 `GO2_OSQP_ROOT` 指定成对的 `include/osqp` 与 `lib/libosqp.so`。仅将 OSQP C 头文件目录加入编译，通过绝对路径在启动时动态装载 C API；不将整个 Conda 前缀加入 CMake/Pinocchio 搜索路径。当前 C 库仅依赖 qdldl 和系统 C 库，已核对并测试。更换部署机器时需配置并验证对应平台的 C 库和 ABI，不直接复制本机二进制。

未设置 `GO2_OSQP_ROOT` 时仍可构建模型检查；设置后才启用 WBC 库和 `wbc_replay`。构建脚本会传入本机已验证的前缀，可通过 `GO2_PYTHON` / `GO2_OSQP_ROOT` / `GO2_WORKSPACE` 覆盖路径。

## 本地 MRT 与 C++ MuJoCo 闭环（2026-10-15）

### 控制链

```text
启动前：Python 生成既有 IK 目标时间表及参考转换对照样本 → JSON

外部 OCS2 DDP/SLQ MPC ← 每 20 ms 的实测观测
           ↓ 策略 ROS 消息
C++ ROS 接收线程：校验、解码、准备最多 8 条策略
           ↓ 每 4 ms 尝试采用有效的新策略
C++ 控制线程：MuJoCo 状态 → 质心状态 → 本地 MRT 双时刻求值
           → 基座/足端参考 → WBC → 关节 PD → 力矩映射与限幅 → mj_step
```

逐步控制不调用 Python 管道或 MRT ROS 查询服务。Python 只在启动前生成目标，在运行结束后汇总 CSV；MPC 暂时保持外部进程，与控制进程通过观测/策略消息连接。没有将 MPC 改为同进程求解线程。

| 文件 | 职责 |
| --- | --- |
| `include/go2_control_cpp/reference.hpp` / `src/reference.cpp` | 显式关节名映射；质心状态与四元数 q/v 双向转换；基座、接触力和摆腿参考 |
| `include/go2_control_cpp/local_mrt.hpp` / `src/local_mrt.cpp` | 一次 reset、策略校验与接收线程、策略选择和本地 MRT |
| `include/go2_control_cpp/simulation.hpp` / `src/simulation.cpp` | MuJoCo C API、状态与力矩映射、地面接触力、官方 Simulate 被动查看器 |
| `src/control_simulation.cpp` | 2 ms 仿真步、观测/策略时序、WBC、PD、异常停止与 CSV |
| `examples/mujoco/prepare_cpp_target.py` | 复用既有 Python IK/目标函数，生成 401 个目标点和三组转换对照 |
| `scripts/build_cpp_control.sh` | 使用 ROS Pinocchio 和明确的 OSQP/MuJoCo 路径构建 |
| `scripts/run_cpp_simulation.sh` | 准备目标、启动配套 MPC、运行、汇总，退出时关闭自己启动的 MPC |
| `tools/summarize_cpp_control.py` | 检查完整采样、身份/年龄及残差，汇总运动、接触和时序 |

### 坐标和策略约定

- OCS2 关节顺序从目标 JSON 读取并与 `task.info` 完全核对，再按名称映射到 Pinocchio。力按 FL/FR/RL/RR 及 mode 的实际支撑足映射。MuJoCo 电机也按名称匹配，并验证为直接力矩驱动。
- 当前和未来 5 ms 参考在同一次激活的策略上求值，期间不切换 active policy。未来 mode 独立检查；只有该足在两个时刻都处于摆动时，才差分足端速度得到加速度。
- 摆腿采用现有 Python `--swing-reference mpc` 路径：位置和速度来自 MPC 参考的 FK。关节 PD 采用同一时刻的关节参考，kp=20、kd=1，单独叠加到 QP 力矩后限幅。
- ROS 线程先完成解码，再用短互斥区传递准备好的对象。控制侧 try-lock 选择策略；激活和两次求值均由控制线程执行，epoch/sequence 元数据随同一对象切换。运行中禁止再次 reset。
- 仅接受 feedforward、24 维状态/输入和 mode 15/9/6。检查 epoch、递增 sequence、观测时间不倒退、有限值、轨迹尺寸和时间表。采用策略时要求覆盖下一次检查与未来查询，逐步检查年龄不超过 100 ms 和当前/未来查询覆盖。
- `MRT_ROS_Interface` 作为官方解码/求值的基类；本地封装自行接收消息和调用 reset 服务，没有调用 `launchNodes()` 或另起查询服务。

最终实现：

1. 每个求解器累计保留已出现过的 H 上三角及 A 存储位置；数值变零不删除，首次出现新位置时扩容并重建一次。问题维数改变时重置位置集合。使用精确零判断，不丢弃小数值，不预留永远未出现的整块零。该方案允许启动/新工况出现少量扩容，并非从第一步就完全禁止重建。
2. 同次更新先调用 `osqp_update_data_vec`，再调用 `osqp_update_data_mat`。矩阵更新内部会 unscale/scale，此时需让工作区持有本步 q/l/u；顺序与本地 OSQP Python 接口相同。可参见 [OSQP 更新实现](https://github.com/osqp/osqp/blob/master/src/osqp_api.c)及[Python 接口](https://github.com/osqp/osqp-python/blob/master/src/osqp/interface.py)。
3. 保存初始化时的默认 rho，复用时通过 `osqp_update_rho` 恢复，保持本轮冷求解与新工作区的数值一致性。`warm_starting=0` 清零迭代变量不会同时重置自适应 rho；同一 QP 的迭代路径可能受先前 rho 影响。该额外更新也有分解成本，不能只凭初始化减少就推断循环加速。

7～11.8 s 前进段，四足触地时真实球心的平均 x 速度分别为 0.01408/0.01250/0.01342/0.01454 m/s（FL/FR/RL/RR）。相应由角速度与半径推得的滚动速度为 0.00836/0.00807/0.00940/0.01004 m/s。排除每次触地的前 20 ms 后，真实球心速度与滚动模型的平均 x 差值为 +0.000208/+0.000181/-0.000226/-0.000268 m/s；主要差异集中在触地初段。这一证据支持同时处理球心运动和触地过渡，不将全部球心位移当作打滑，也不是关节顺序或足端 FK 错误。

原理对应代码如下。记足端球心相对基座的向量为 `r = p_foot - p_base`，则：

```text
dr/dt = v_foot - v_base
v_base = v_foot - dr/dt
```

旧速度观测把 `v_foot` 设为零。球形脚即使瞬时接触点不滑，转动时球心也能移动。在当前平地模型中，接触点相对球心为 `-radius * world_z`，因此：

```text
0 = v_center + omega_foot × (-radius * world_z)
v_center = omega_foot × (radius * world_z)
```

`estimator_preprocessor.cpp` 使用 IMU 和关节运动学得到足部角速度，按现有球半径 0.022 m 生成 `supported_velocity_world`，没有用真实足端速度做补偿。实际接触标志为真后，先等待 20 ms，再在随后 20 ms 内将 `contact_trust` 从 0 升至 1；离地清零。该设置针对本轮观测到的触地瞬态，真实传感器及不同地面仍需验证。

`state_estimation.cpp` 同时修改预测和观测：支撑足位置按球心滚动速度推进；无可信支撑时，按 `v_foot = v_base + dr/dt` 推进足状态，在状态转移矩阵中保留对基座速度的依赖，并加入对应的加速度位移项。速度观测改为 `supported_velocity_world - velocity_relative_world`；可信度为零时移除该脚的支撑速度及地面高度观测，足端相对位置观测保留。中间可信度用于过渡和噪声缩放。状态维数仍为 18，Joseph 协方差更新保留。

## 共用关节命令（2026-10-20）

传感器启动节点已提交并推送为 `17a468b`。继续在 `feature/sensor-startup` 上整理执行接口，新增 `JointCommand`：每个关节保存目标位置 q、目标速度 dq、Kp、Kd 和前馈力矩，另有当前控制步的时间戳。数组顺序与 `RobotModel::motor_names` 及 `SensorMeasurements` 一致；目前依次为 FR、FL、RR、RL，每腿 hip/thigh/calf。这不是已经核验的实机 SDK 索引映射。

统一执行公式为：

```text
tau = tau_ff + Kp * (q_des - q_sensor) + Kd * (dq_des - dq_sensor)
```

- 准备阶段：q_des 是名义准备姿态，dq_des=0，Kp=60，Kd=3，tau_ff=0。
- 运行阶段：q_des/dq_des 来自 MRT 当前参考，Kp/Kd 来自运行参数，tau_ff 来自 WBC 解中的关节力矩。当前验收参数 Kp=0、Kd=1，因此运行时仍保留速度反馈。
- 接管阶段：混合两条力矩规律。有效 Kp 是 `w*Kp_prep+(1-w)*Kp_run`，q_des 用 `Kp*q_des` 的加权和除以有效 Kp；Kd/dq_des 同理。有效增益为零时对应目标取有限零值，端点直接返回对应命令。这样生成的命令保持 `w*tau_prep+(1-w)*tau_run` 的原有力矩关系；不能把位置和增益分别普通平均后相乘。

`Simulation::command()` 读取该命令与本步关节传感器，计算总力矩，按关节名映射到 MuJoCo 执行器，再进行原有总力矩限幅。命令检查有限值、非负增益及与测量一致的时间；仿真入口还核对测量时间与当前仿真时间一致。此时间检查是当前同步仿真约定，尚非真实 DDS 数据新鲜度处理。结束时使用 `clearCommand()` 清空仿真执行力矩，行为仍是停止仿真，并非实机停止方案。

CSV 保留前 195 列顺序，末尾新增每个命名关节的五个命令字段，共 255 列，例如 `cmd_FR_hip_joint_q_rad`、`cmd_FR_hip_joint_dq_radps`、`cmd_FR_hip_joint_kp`、`cmd_FR_hip_joint_kd`、`cmd_FR_hip_joint_tau_ff_nm`。记录的是发往执行入口的混合后命令；汇总检查 12 个关节字段完整、增益与接管权重一致、纯准备阶段前馈力矩为零。JSON 标注实机映射未验证。

### CRC 与输入检查

CRC 按该 SDK 示例的 32 位字序和多项式计算。当前 LowCmd 对象大小为 812 字节；检查器核对 CRC 为最后 4 字节、float 为 IEEE 32 位及小端布局。构造前清零全部字节（包含参与 CRC 的 ABI 填充），最后在调用者提供的最终对象中写入 CRC。计算使用 memcpy 读取字，避免示例指针转换的对齐/别名问题；参考算法及 SDK 的 BSD-3-Clause 条款保存在同目录 `UNITREE_LICENSE`。

适配器检查现有命令的有限性、非负增益及 double 到 SDK float 的可表示范围；数值溢出会被拒绝。时间字段仅保留现有命令验证，**未执行真实数据新鲜度、总力矩/物理限位、电机健康或控制权检查**，这些属于后续真实读写环节。CRC 用于检查消息内容一致性，不代表动作已经通过物理验收。

### 原理与代码路径

对角速度、加速度计比力和关节角/角速度，实际使用值为 `measured = raw + bias + sigma * normal(0, 1)`：bias 是每次运行不变的偏置，sigma 是每轴、每次采样的标准差。sigma 不是误差最大值、噪声密度，也不是 `KalmanNoise` 内的协方差缩放参数。姿态误差用 IMU 局部坐标系旋转向量表示，`R_measured = R_raw * Exp(bias + noise)`，通过右乘误差四元数并归一化实现，不直接修改四元数四个分量。

`SensorErrorSettings` / `SensorErrorModel` 位于 `sensor_errors.hpp/.cpp`；独立库仅依赖 Eigen、标准库和 Boost JSON 头文件。固定 `std::mt19937` 种子和相同采样顺序可在当前 C++ 标准库/工具链重现噪声，未声明跨标准库实现逐位一致。相同物理样本重复读取复用已生成值，避免启动 t=0 被重复采样两次。无配置时所有标准差和偏置均为零，输出原样保持。

数据通路：MuJoCo 原始传感器 → 测量误差模型 → 准备姿态/初始高度与滤波初始化 → Kalman / MPC / WBC → 关节反馈执行。模拟关节执行器也使用实际送入控制的关节测量计算 `tau_ff + Kp*(q_des-q_measured) + Kd*(dq_des-dq_measured)`，之后按已有执行器范围限幅。本轮统一给上层和模拟关节反馈使用同一份带误差读数；真实电机内部反馈与上报状态的噪声/频率关系尚未建模。

原始关节/姿态/角速度与仿真状态的严格映射检查继续保留。额外的原始测量预处理实例仅用于运动学核对，不参与估计修正；带误差测量的足端运动学偏差另行记录。启动首条 MPC 观测及后续机身位置/速度来自测量/估计，真值只用于检查、状态边界和统计。时间戳、接触标志继续保持原有来源，配置要求 `--sensor-startup`，避免误将真值控制运行当成带误差闭环验证。

事件参数：`--sensor-event delay|dropout|contact-on|contact-off`、`--sensor-event-at`、`--sensor-event-duration`，以及默认 2 ms 的 `--sensor-delay-ms`、默认左前脚的 `--sensor-contact-foot fl|fr|rl|rr`。起点 ≥3 s，时间按 2 ms 对齐；延迟范围 2–100 ms，要求 `--sensor-startup`，每次运行仅配置一种事件，完整事件区间须位于请求会话时长内。接触数组顺序为 FL/FR/RL/RR。
