# 控制循环逐步耗时分析

## 状态与目标

2026-10-15，在 `feature/ocs2-control-timing` 为 OCS2–WBC–MuJoCo 实验接入每步分段计时及独立 CSV，已完成 20 s 异步前进和停步。此次增加测量，不改变 MPC/WBC 参数、步态、目标轨迹或策略选择规则。排除前 2 s 后，9000 步中有 1820 步超过 2 ms，其中 1714 步以 MRT 查询往返为最大耗时项；下一步优先分析该查询路径内部的通信等待和 C++ 求值成本。

此前 4 ms 策略检查下，前进及左右转的循环平均耗时约 1.70–1.74 ms，p95 约 2.5 ms，仍有控制步超过 2 ms。逐步记录用于将某一次超时与当步各阶段耗时对应，决定下一项通信或 C++ 控制循环改动，不能只用全程平均值判断固定 500 Hz 是否满足。

## 分段口径

每步从主动节拍等待结束后的 `loop_start` 开始，以连续时间点划分以下互不重叠的阶段，单位均为 ms：

| 字段 | 范围 |
| --- | --- |
| `state_ms` | MuJoCo 状态映射、当前目标计算与状态检查 |
| `policy_ms` | 到期的 plan/observe/poll、策略年龄及覆盖检查、当前质心状态转换和查询准备 |
| `mrt_pair_ms` | 一次双时刻 MRT 请求，含 Python 管道、ROS 服务往返和响应解析 |
| `reference_ms` | mode 核对、控制器选择、足端运动学、当前/未来 WBC 参考及加速度前馈 |
| `wbc_ms` | WBC 求解和求解结果/约束残差检查 |
| `command_ms` | 关节参考转换、现有 PD 参考差异诊断、关节 PD、力矩映射、限幅及写入 MuJoCo 控制量 |
| `logging_ms` | 主运动记录组装、力顺序转换、终端每秒打印及其 lookahead 诊断 |
| `simulation_ms` | `mujoco.mj_step` |
| `contact_ms` | 地面接触力/速度诊断、接触历史更新及本步运动记录补全和入队 |
| `viewer_ms` | 条件分支及可选窗口同步；无窗口时通常接近零 |
| `timing_record_ms` | 最后阶段结束后到循环计时结束之间，分段耗时及计时行的组装、入队 |
| `loop_ms` | 从 `loop_start` 到本步计时行入队后的总耗时，含上述各段 |

时间来源为 `time.perf_counter()` 的墙钟时间，包括等待和被调度暂停的时间，不等同于 CPU 计算时间。各标记的少量记录成本也会落在相邻阶段；`timing_record_ms` 不代表全部测量成本。最终回填总耗时及下一步准备等少量操作发生在最后计时点之后。

现有 `timing_ms.wbc` 只包住求解调用，新 `wbc_ms` 还包含结果检查。旧 `timing_ms.plan/observe/poll` 是 `policy_ms` 的子项，不能将两组数直接相加。单步分段与 `timing_record_ms` 之和应等于 `loop_ms`；程序检查有限性、非负性及求和误差（容差 1e-6 ms）。各段 p95/p99 的和不等于整步 p95/p99。

## 数据对应与初始化

主运动 CSV 保留原来的 103 列。新增计时 CSV 包含 22 列：step、积分前的 time_s、mode、初始化标记、plan/observe/poll 调用标记、策略更新标记、策略年龄/启动迟到量，以及 12 个耗时字段。程序检查计时记录与运动记录的样本数、time_s 和 mode 一一对应。

MuJoCo 推进之后使用本步运动行保存的 time_s，避免计时行被错误标记到下一步。策略年龄及启动迟到量在计时 CSV 中使用 ms，主 CSV 中仍为 s；同步模式对应值为 NaN。

所有样本都写入计时 CSV，首次初始化所在行的 `initialization_step=1`。新增 `control_timing` 汇总沿用运动评估区间：通常排除前 2 s，短于该区间的实验使用全部样本。完整 20 s、2 ms 步长的正常运行预计有 10000 行计时数据，其中 t ≥ 2 s 的汇总样本为 9000。原有整轮计时和超时计数仍包含初始化，因此可能与新增汇总不同。

## 运行与输出

先按[异步实验说明](ocs2_async_mpc.md#首次-20-s-站立验证)启动 ROS_DOMAIN_ID=214 的 MPC 与支持双时刻接口的 MRT 节点。本次只修改 Python，无需重建 ROS 包。仿真终端执行：

```bash
env -u PYTHONPATH ROS_DOMAIN_ID=214 \
  /home/bot/miniconda3/envs/go2_control/bin/python \
  examples/mujoco/ocs2_wbc_standing.py \
  --headless --duration 20 --async-mpc \
  --allow-trot --trot-at 3 --stop-trot-at 15 \
  --forward --swing-reference=mpc \
  --csv artifacts/ocs2_wbc_forward_control_profile.csv
```

输出均在本地 `artifacts/`，不随 Git 提交：

- `ocs2_wbc_forward_control_profile.csv`：原运动和接触记录。
- `ocs2_wbc_forward_control_profile_timing.csv`：逐步分段耗时。
- `ocs2_wbc_forward_control_profile.json`：原汇总及新增 `control_timing`。

未传 `--csv` 时仍进行内存记录并打印汇总，不写文件。文件写入和运行后统计均在控制循环结束后执行。

## 分析方法与验证范围

`control_timing` 输出每段及整步的 mean/p95/p99/maximum、评估区间超时数、超时步中各段的平均耗时，以及超时步中各段成为最大耗时项的次数。最大项计数只是描述，不能单独证明因果；遇到相同最大值按字段顺序计入首项。

先排除初始化，再按 mode、观测发布步、策略检查步及日志打印附近样本分析。区分必要控制计算、通信等待和仿真诊断，并结合主 CSV 的策略年龄、启动迟到及接触状态，决定下一项改动。当前 `command_ms` 仍包含一项诊断，`reference_ms` 也包含脚部运动学，不能把某些阶段简单宣称为纯控制或纯诊断成本。

已通过语法编译、`git diff --check` 以及定向离线检查：初始化排除、超时统计、无超时情况、分段求和不一致和负数/非有限耗时的拒绝。随后完成下述真实 ROS/MuJoCo 20 s 集成运行，未重复完整 pytest。新计时会增加开销并可能影响异步调度，不能将前后两次运行的全部耗时或动作差异归因于计时语句。

## 2026-10-15 前进停步计时结果

上述命令完成 10000 步，主运动 CSV 为 103 列，计时 CSV 为 22 列，两份文件的 time_s、mode 逐元素一致。运行中分段求和误差为 0，CSV 按 `%.10g` 保存后重新读取的最大求和差约 1.05e-8 ms，属于输出舍入误差。计时文件标记的 plan/observe/poll/策略更新次数为 1/999/5000/999，与原汇总一致。

### 持续运行与初始化分开统计

| 指标 | 全程 10000 步 | t ≥ 2 s 的 9000 步 |
| --- | ---: | ---: |
| 循环平均 | 1.817 ms | 1.756 ms |
| 循环 p95 | 2.666 ms | 2.672 ms |
| 循环 p99 | 未在旧汇总计算 | 2.900 ms |
| 最大循环耗时 | 778.859 ms | 8.914 ms |
| 超过 2 ms 的步数 | 1999 | 1820 |

首次 plan 约 774.874 ms，属于初始化等待。持续运行中的最大值应参考 8.914 ms，不能将 778.859 ms 当作每次查询的计算峰值，也不能因为平均 1.756 ms 低于步长就声称稳定 500 Hz。

### 超时步特征与下一项改动

1820 个超时步的平均整步耗时为 2.565 ms，MRT 往返平均 1.167 ms、WBC 平均 0.662 ms。非超时步对应整步平均 1.551 ms，MRT 0.338 ms、WBC 0.626 ms。超时步的最大项计数为 MRT 1714、WBC 105、策略处理 1；即 94.2% 的超时步以 MRT 为最大项。该统计描述相关性，不等于已证明 94.2% 的超时都由 C++ MRT 算法造成。

最慢持续运行样本在 t=11.430 s、mode=6，整步 8.914 ms，其中 MRT 往返 7.350 ms、WBC 0.867 ms、参考转换 0.413 ms。当步未 poll 或发布观测，说明额外延迟并不只发生在新策略检查步。两足模式下 WBC 均值约 0.722–0.724 ms、四足模式约 0.514 ms，而各模式 MRT 均值均约 0.502–0.507 ms。

进一步按调度标记分组：

| t ≥ 2 s 的样本组 | 步数 | 超时步数 | 循环平均 | MRT 平均 |
| --- | ---: | ---: | ---: | ---: |
| 有 poll | 4500 | 1537 | 1.943 ms | 0.593 ms |
| 无 poll | 4500 | 283 | 1.570 ms | 0.419 ms |
| 发布观测 | 900 | 30 | 1.733 ms | 0.314 ms |
| 未发布观测 | 8100 | 1790 | 1.759 ms | 0.527 ms |

poll/观测标记与执行相位、策略到达和系统调度相关，不能把分组均值之差直接解释为一个函数的独立开销。当前数据支持优先细分 MRT 查询路径，区分 Python 管道/JSON、rclpy 服务等待、C++ 策略激活和两次求值，再决定本地 C++ MRT 接入方式。此项尚未修改。WBC 也有 4.913 ms 峰值，仍需在部署控制循环中关注。

### 动作与时效核对

首次双足模式在 4.042 s，持续四脚支撑从 16.000 s 开始。前次 4 ms poll 前进运行首次双足模式为 4.022 s；计时语句不改变策略规则，但异步调度使本轮轨迹并非逐步完全相同。最终 x 为 0.090411 m，相对 0.09 m 目标误差 +0.411 mm；8–12 s 外部 x 目标 RMSE 为 12.211 mm，最大落后 17.625 mm，与前轮 12.218/17.608 mm 接近。

四脚支撑实际触地比例均为 100%，摆动中段触地样本均为 0；最大电机力矩 16.709 N·m，未限幅。动力学/接触加速度残差最大约 2.00e-6/4.13e-7，OSQP 为 4 次 setup、9996 次 update。策略年龄中位数/p95/最大值为 22/32/38 ms；启动迟到量中位数/p95/最大值为 0.0570/1.514/7.306 ms，末步 0.218 ms。

此轮提供了计时功能与前进闭环的验证，可保存为后续通信改动的基线。CSV/JSON 保存在前述本地路径，未提交；源码及实验说明随阶段提交。
